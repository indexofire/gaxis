# Core Concepts

Understanding the six concepts below means understanding all of gaxis's behavior.

## 1. A chart = script + artifact + manifest

A single render produces three things, and they must exist together:

```
data/renders/bar-65ca394dac/
  figure.py                    # deliverable script, does not import gaxis
  bar-65ca394dac.pdf / .png    # outputs (requested formats)
  manifest.json                # evidence: data.sha256, code_sha256, geometry, lint
```

- **`figure.py` is the deliverable, not a build intermediate.** It runs in a clean Python environment on its own.
- **`manifest.json` is the evidence.** If either the data or the code changes, the hash changes; so does `figure_id`.
- **A chart without a manifest is not an artifact.** By rule, every render path must write a manifest.

`figure_id` is determined by `PIPELINE_VERSION + data hash + spec`. Whenever the template or emission changes, the version number must change, so old code is never mistaken for current output.

## 2. Three scores, never merged

| Score | Question it answers | Location |
|---|---|---|
| `chart_quality_score` | Is this **extracted chart** usable? (caption, clarity, cropping) | manifest / KB |
| `design.score` | Is this chart **well designed**? (aesthetics + information design) | manifest / KB |
| `usefulness_score` | Is this chart **worth reproducing**? (journal, statistics, validation, panels, caption) | manifest / KB |

Extraction quality is a **gate**, not an aesthetic judgment; the design score is a review verdict and stays `null` until reviewed; usefulness drives ranking. Retrieval sorts by `0.7 × design + 0.3 × usefulness` by default (configurable via `[ranking]`).

## 3. Reproduction levels L1 / L2 / L3

| Level | Meaning | Evidence |
|---|---|---|
| **L1** | Code runs, and the render closely matches the paper figure (≥ `[reproduction] l1_similarity`) | sandbox report + similarity breakdown |
| **L2** | Runs and is structurally similar, but values/styling differ | similarity breakdown + failure reason |
| **L3** | Code runs, but visually very different; usable as a **style/logic reference** | run log + failure reason |
| **none** | Not run, blocked (license/static scan), or run failed | explicit reason, never hidden |

Level is the primary sort key: at equal relevance, L1 > L2 > L3 > none. Assets with `level=none` sort last by default — that is by design, not a bug.

## 4. Sandbox and evidence

Paper code runs in **rootless podman** by default:

```
--network none  --read-only  --cap-drop ALL  --pids-limit  --memory  --cpus  no-new-privileges
```

- Every run records the resolved **image id**; switching images invalidates old grades, and gaxis records this explicitly rather than comparing silently.
- Licenses are a gate: GPL/AGPL code may be recorded (for reusing logic), but it is **never** copied into templates and never run in the sandbox.
- Static scanning blocks dangerous patterns such as `os.system`, `eval`, and `exec`.
- The `local` engine is for development and testing only; reports always state `network_enforced: false, read_only_root: false`.

!!! warning "local is not secure execution"
    Results from the local engine must not be treated as evidence of "secure execution" and must not appear in external conclusions.

## 5. Knowledge base: manifests are the source of truth, pages are the index

```
data/manifests/*.json        ← authoritative: the facts about paper figures
        │  kb ingest (idempotent, by content hash)
        ▼
gbrain source `paper-kb`      ← derived: rebuildable pages (body + filterable frontmatter)
        │  search (text / table shape / image dHash)
        ▼
candidates → contact sheet → you pick one → render / adapt
```

- Pages can be deleted and rebuilt at any time; manifests cannot.
- Templates (`type: template`) are a different kind of page: they are generated by `gaxis kb seed`/`kb adopt`, recording the code hash and interface.
- `search_chart_assets` queries only `type: analysis` (paper figures) by default; templates never mix into paper candidates.

## 6. Two data classifications

Every MCP tool declares a `data_class`:

| Class | Meaning | Examples |
|---|---|---|
| `D1` | Public data | search, manifests, paper ingestion |
| `D3` | Reads local user files | `render_chart_from_data`, `adapt_chart_code`, `compose_panels` |

The host (e.g., bacmap) filters by profile before invoking: the cloud profile sees only D1 tools; only the local trusted profile sees all 10. This is a guarantee at the **boundary** level, not one that relies on tools behaving themselves.

## How the concepts relate

```text
DataSchema ──► ChartSpec ──► emit(script) ──► run ──► outputs + lint
                   ▲                                  │
                   │                                  ▼
        KB template ─┘                              manifest
                   ▲                                  │
       paper code ─┘(reproduce / adopt)                  ▼
                                                KB page ──► search
```

The three producers (built-in templates, KB templates, and paper reproduction) share a single render path, so "generated charts" and "reproduced charts" can never drift.
